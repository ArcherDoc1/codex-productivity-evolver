# 设计理念

## 为什么需要这个 skill

普通工程协作里，真正消耗时间的往往不是“写一条命令”，而是：

- 没确认路径就改错目录。
- 没看日志就重装依赖。
- 没备份就覆盖配置。
- 没验证就宣布完成。
- 同一个问题下次又从零排查。

`codex-productivity-evolver` 的目标是把这些容易遗漏的工程习惯变成默认动作。

## 工作模型

```text
确认目标 -> 检查真实状态 -> 风险分级 -> 小步实施 -> 验证 -> 总结沉淀
```

## 风险分级

低风险任务：

- 只读检查、文档、局部样式、小脚本。
- 可以直接推进，但仍需要说明验证结果。

中风险任务：

- 配置、依赖、启动参数、数据查询、自动化脚本。
- 需要说明影响范围，尽量保留备份或可回滚路径。

高风险任务：

- 删除、清理磁盘、SSH、防火墙、生产服务、认证信息、批量数据。
- 需要先给计划、风险、备份和确认点。

## 输出风格

- 中文优先。
- 先结论，再原因。
- 命令可复制。
- 少讲泛泛原则，多给具体检查路径。
- 对不能验证的地方明确说不能验证，而不是假装完成。

## 进化方式

一次任务结束后，可以把经验沉淀为四类内容：

- 检查清单：以后先看什么。
- 禁止动作：哪些事情不能直接做。
- 推荐命令：可复制的最小命令。
- 验证方式：怎样证明真的修好了。
